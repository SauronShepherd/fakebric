## Selector de ejecución

`fakebric/native_selector.py` introduce el contrato versionado `QueryExecutionRequest` y el selector `jvm/native/auto/compare`.

- `jvm` ejecuta únicamente JVM.
- `native` es estricto: exige doble opt-in global + sesión y un plan compatible; no cae silenciosamente a JVM.
- `auto` puede usar native cuando está habilitado y el plan es compatible, y recurrir a JVM una sola vez ante incompatibilidad o fallo native recuperable.
- `compare` queda preparado para solicitar ambos backends, pero JVM sigue siendo autoritativo y la ejecución dual real queda bloqueada hasta el comparador de resultados del Día 7.

## Fallback exactamente una vez

Los fallos native recuperables mapeados son:

- `NATIVE_INIT_FAILED`;
- `NATIVE_EXECUTION_FAILED`;
- `NATIVE_TIMEOUT`;
- `NATIVE_OOM`.

En modo `auto`, un fallo de ese conjunto produce como máximo un intento JVM adicional. Si el intento JVM falla, el selector no reintenta de nuevo.

Un `NATIVE_SECURITY_POLICY` no se convierte nunca en fallback: no se ejecuta ningún backend.

## Preservación de semántica de consulta

Antes de ejecutar se captura un snapshot canónico de:

- statement;
- parámetros;
- filtros;
- orden;
- límite.

Cada backend recibe una copia independiente de ese snapshot. Por tanto, aunque el intento native mutase accidentalmente su objeto de request antes de fallar, el fallback JVM recibe exactamente el payload original.

## Backend solicitado y backend efectivo

La decisión y los diagnósticos diferencian explícitamente:

- modo solicitado;
- backends solicitados;
- backends intentados;
- backend efectivo final;
- motivo de fallback;
- número de fallbacks.

Si native falla y JVM completa la consulta, el backend efectivo final es `jvm`; no se reporta falsamente éxito native.

## Redacción
